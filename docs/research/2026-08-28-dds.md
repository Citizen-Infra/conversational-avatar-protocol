# Decentralized Deliberation Stack: boundary lessons for CAP

**Source:** [`dds-wg/dds`](https://github.com/dds-wg/dds), reviewed at [`052a92aa9b14953c6101f56f1e7c78362a517249`](https://github.com/dds-wg/dds/tree/052a92aa9b14953c6101f56f1e7c78362a517249) on 2026-08-28, including the Working Draft, August plenary material, governance agreement, and the open DEL/DDS relationship discussion.

**Status:** Public research summary. This comparison defines an adjacent interoperability boundary. It is not a claim that DDS has adopted community avatars as a use case.

## Verdict

DDS is a valuable compatibility surface for deliberation artifacts and process records. It is not currently the home or owner of avatar-participation semantics.

CAP should remain independently stewarded unless DDS explicitly chooses community avatars as a work item. If a real integration later needs CAP contributions to travel through DDS-compatible records, define the smallest evidence-led mapping rather than making either initiative depend on the other.

## What DDS is becoming

DDS describes itself as an open stack for sovereign, verifiable, interoperable, and resilient deliberation. Its August plenary material broadens the work beyond its original AT Protocol starting point and describes a protocol-agnostic profile lifecycle.

The lifecycle is:

- **Use Case:** context, participants, deliberation flow, and intended outcomes.
- **Draft Profile:** product- and protocol-independent required features, ontology, broad UX, safety, and expectations.
- **Profile Validation:** research, stakeholder review, scenarios, and pilots.
- **Recommended Profile:** reviewed requirements and implementation-validation criteria.
- **Draft Implementation Profile:** mapping to real products, protocols, versions, and configurations.
- **Implementation Validation:** audits, research, and real-world tests.
- **Recommended Implementation Profile:** tested package with evidence, limitations, and trade-offs.

This is a useful standards-development pattern: validate the product-independent requirement before recommending one implementation profile.

## The current specification and direction differ

The checked-in Working Draft still describes a specific architecture involving AT Protocol, decentralized storage, and Ethereum. The plenary material says DDS is now protocol-agnostic and organizes future work through profiles and tracks.

That means the profile lifecycle is directional evidence, not yet a complete replacement for the current specification. CAP should not claim compatibility from the slides alone; any mapping must target a reviewed DDS artifact and version.

## What DDS covers well

DDS's emerging tracks and artifacts cover concerns adjacent to CAP:

- Deliberation use cases, flows, participation rules, facilitation, and decision handoff.
- Core deliberation concepts, lifecycle, provenance, and mappings.
- Protocol bindings, identity, portability, archival, recovery, and bridges.
- Clustering, summarization, sensemaking, metrics, bias, and human review.
- Deterministic re-execution, audits, evidence reports, and proof systems.
- Product-independent profiles validated through scenarios and pilots.

These can describe the process and records in which an avatar contribution appears without defining the avatar's mandate or runtime.

## The missing avatar actor

At the reviewed snapshot, DDS has no defined community-avatar actor, representation mandate, or avatar participation exchange. Its current specification includes analysis and archive agents, but those roles do not establish authority to act as a community's disclosed representative.

The open discussion about the Deliberation Ontology (DEL) asks whether DDS should reference, map to, or remain separate from an existing deliberation ontology. DEL's broader participant vocabulary, including artificial agents discussed in that thread, is ontology input. It is not evidence that DDS has adopted agents acting as community avatars.

A generic profile or extension mechanism is also not evidence that its maintainers want every possible compatible use case inside DDS scope.

## Boundary between DDS and CAP

| Concern | Best current home |
|---|---|
| Deliberation artifacts, lifecycle, and process records | DDS |
| Deliberation ontology and record mappings | DDS or its chosen ontology relationship |
| Avatar identity, represented community, operator, and mandate | CAP |
| Authority limits, disclosure, abstention, and evidence envelope | CAP |
| Turn exchange between avatar runtime and deliberation platform | CAP |
| Brain ingestion, retrieval, prompts, models, freshness, and runtime state | Avatar runtime specification |
| One-time community configuration and implementation kickoff | `avatar-init` |
| Reusable libraries and platform connectors | Optional Avatar SDK |
| CAP contribution represented in a DDS-compatible record | Optional CAP-to-DDS mapping |

CAP does not replace DDS's deliberation records or process interoperability. DDS does not replace CAP's representative authority and participation exchange.

## When to create a CAP-to-DDS mapping

Create a mapping only when a concrete integration needs one. The integration should identify:

- The actual DDS profile, ontology, or record version in use.
- Which CAP contribution and evidence fields must round-trip.
- Which concepts map directly, need an extension, or must remain external.
- How correction, withdrawal, provenance, and finality survive the mapping.
- What evidence demonstrates that two implementations preserve meaning.

The mapping should be optional and versioned. It should not turn CAP into a DDS work track or make the first avatar pilot wait for DDS scope decisions.

## Lessons CAP can adopt without coupling

### Use profiles to separate requirements from implementations

CAP can define transport-neutral avatar semantics and publish separate implementation profiles or bindings for MCP, HTTP, a deliberation platform, or a future DDS record mapping.

### Validate through scenarios and pilots

DDS's lifecycle supports CAP's decision to prove one participant vertical slice before publishing a stable protocol. A candidate becomes a recommendation only after stakeholder review and implementation evidence.

### Preserve plurality and credible exit

A CAP contribution should not depend on one deliberation vendor, identity system, storage network, or model provider. Bindings and mappings should let communities change implementations without losing the meaning or provenance of representative contributions.

### Keep recommendation claims precise

DDS distinguishes a recommended profile from product certification, endorsement, or a W3C Recommendation. CAP should make equivalent maturity labels explicit and prohibit conformance claims before a versioned protocol and test suite exist.

## What CAP should not copy prematurely

- The current AT Protocol, decentralized-storage, or Ethereum architecture as an avatar requirement.
- A generic deliberation ontology as proof of representative authority.
- Analysis-agent or archive-agent roles as substitutes for a disclosed participant mandate.
- A CAP-to-DDS mapping without a concrete record integration.
- DDS ownership or endorsement claims not made by the Community Group.

## What remains unproven

No reviewed source demonstrates that DDS maintainers want community avatars in scope. No implementation has shown that a CAP evidence envelope round-trips through a DDS profile or ontology without losing authority, correction, or finality semantics.

Until such evidence exists, compatibility remains an option rather than a dependency.
